Single Sign-On for Service Grid

Single Sign-On (SSO) is a concept that allows a user to log in once with a single set of credentials and access multiple applications without re-authenticating.

OpenID Connect (OIDC) is an authentication protocol built on top of the OAuth 2.0 authorization framework that enables SSO. It's the technical standard that makes "Sign in with Google" or "Sign in with Facebook" possible.

Since version 17.1.5, SSO is also available in the service grid installation.

To use SSO you must first define the IDP and use the groups field for specifying roles.

See SpaceDeck - SSO IDP Setup for IDP setup example.

Setting up a cluster with SSO in Service Grid

  1. Edit gs-home/config/security/openid-security.properties:

    com.gs.security.security-manager.class=com.gigaspaces.security.openid.OpenIdSecurityManager

    # OpenID Provider Configuration

    com.gs.openid.clientId=com.gs.openid.clientSecret=com.gs.openid.issueURL=com.gs.openid.redirectUris=http://<xap-manager-host>:9000/oauth2/authorization-code/callbackcom.gs.openid.authorityClaim=groups (default roles fields)com.gs.openid.id=1com.gs.openid.spacedeckUrl=https://<xap-manager-host>:8888/api/auth/logincom.gs.openid.providerType=OKTA (as example)spring-security-config-location=../config/security/security-config-openid.xmlspring.config.additional-location=file:../config/security/security-openid.yaml

  2. Edit gs-home/bin/setenv-overrides.sh to point to the openid security properties and turn on security:

    export GS_OPTIONS_EXT="-Dcom.gs.security.enabled=true -Dcom.gs.security.properties-file=$HOME/config/security/openid-security.properties -Dcom.gs.manager.rest.ssl.enabled=false"

  3. As a result of starting the service grid with the above settings a new security service will be started on the manager machine with default port 9000

    You can see the available REST API for this service at:

    http://<xap-manager-host>:9000/swagger-ui/index.html

  4. In order to use XAP manager api in the secured environment, a token from the security service is required.

    To obtain a token - http://<xap-manager-ip>:9000/oauth2/authorize

    If the user is already logged in, token will be retrieved directly; otherwise, a step redirecting to IDP login will be performed. (use https://www.jwt.io/ for debug tokens)

    The token should be used in xap manager Rest API to access the APIs.

  5. Service accounts are used for long-running services, both for internal services as pipelines and can also be created for external pus or long-running space clients

    See more at: https://docs.gigaspaces.com/latest/security/security-service-account-privilege-mgmt.html

SSO

GigaSpaces supports Single Sign-On (SSO) integration using the OpenID Connect (OIDC) standard. This enables centralized user authentication and access control through standard Identity Providers (IdPs) such as Okta, Keycloak, or Azure AD.

Enabling SSO Security

To activate SSO across the Service Grid, update the environment overrides script to enable security and point to your OpenID configuration file.

Edit gs-home/bin/setenv-overrides.sh and add the following export directive:

export GS_OPTIONS_EXT="-Dcom.gs.security.enabled=true -Dcom.gs.security.properties-file=$HOME/config/security/openid-security.properties -Dcom.gs.manager.rest.ssl.enabled=false"

When the Service Grid starts with these settings, a dedicated Security Service is automatically launched on the Manager host on default port 9000.

Configuring OpenID Provider Properties

Define your SSO settings in your security properties file (for example, $HOME/config/security/openid-security.properties).

Property File Example

# OpenID Provider Identification
com.gs.openid.id=1
com.gs.openid.providerType=OKTA

# Identity Provider Credentials & Issuer URL
com.gs.openid.clientId=<client_id_from_idp>
com.gs.openid.clientSecret=<client_secret_from_idp>
com.gs.openid.issueURL=https://<your-org>.okta.com/oauth2/default

# Browser Flow & Redirect Endpoints
com.gs.openid.redirectUris=http://<host>:9000/oauth2/authorization-code/callback
com.gs.openid.spacedeckUrl=https://<host>:8888/api/auth/login

# Role & Group Claim Mapping
com.gs.openid.authorityClaim=groups

Property Reference

Property Type Required Description
com.gs.openid.id Integer Yes Unique numeric identifier for the OpenID provider configuration.
com.gs.openid.providerType String Yes Identity Provider type (for example, OKTA, KEYCLOAK).
com.gs.openid.clientId String Yes Unique Client ID issued by your IdP.
com.gs.openid.clientSecret String Yes Confidential Client Secret issued by your IdP.
com.gs.openid.issueURL String Yes

Issuer URL of the IdP token server.

  • Okta: https://<your-org>.okta.com/oauth2/default

  • Keycloak: http://<host>:8080/realms/<realm-name>
com.gs.openid.redirectUris URI Yes Callback URI registered with your IdP for the authorization code flow.
com.gs.openid.spacedeckUrl URI Yes Endpoint URL required for the browser login flow through SpaceDeck.
com.gs.openid.authorityClaim String Yes Token claim that contains user roles or groups. Must match the payload emitted by your IdP. (Inspect token claims at jwt.io.)

Authenticating & Accessing XAP Manager REST API

When security is enabled, accessing the XAP Manager REST API requires a bearer token issued by the Security Service.

REST API Documentation (Swagger UI)

You can view and test the available REST API endpoints for the Security Service at:

http://<xap-manager-host>:9000/swagger-ui/index.html

Obtaining an Access Token

Request an authorization token by navigating to: http://<xap-manager-ip>:9000/oauth2/authorize

Authentication Flow:

  • If you are already logged in, the Security Service retrieves the token directly.

  • If you are not authenticated, you will be redirected to your Identity Provider's login page.

Using the Token: Include the token in the Authorization header of your XAP Manager REST API requests: Authorization: Bearer <access_token>

You can decode and debug tokens by pasting them into jwt.io.

Service Accounts for Long-Running Tasks

For non-interactive or background processes, such as data pipelines, external Processing Units (PUs), or persistent Space clients, use dedicated Service Accounts rather than user credentials.

For details on configuring permissions and service accounts, refer to the Service Account & Privilege Management Documentation.

Local Development & Testing with Keycloak

For local testing and validation of OpenID Connect flows, deploy a standalone Keycloak instance using Docker.

Step 1: Start Keycloak Container

Run the following command to start Keycloak in development mode:

docker run -p 8080:8080 \
  -e KEYCLOAK_ADMIN=admin \
  -e KEYCLOAK_ADMIN_PASSWORD=admin \
  quay.io/keycloak/keycloak:21.0.1 start-dev

Step 2: Configure Keycloak Admin Console

  1. Access the console at http://localhost:8080 (log in with admin / admin).

  2. Create Realm: Set up a new realm (for example, demo-realm).

  3. Create Client:

    • Create a new confidential client.

    • Set Client Authentication to ON.

    • Enable Direct Access Grants to allow token retrieval via cURL.

  4. Roles & Users: Create roles and users, then assign the roles to users.

  5. Configure Mappers: Ensure user roles are mapped to the claim specified in com.gs.openid.authorityClaim.

Step 3: Retrieve Token via cURL (Direct Grant)

To retrieve a token programmatically without a browser:

curl -X POST http://localhost:8080/realms/<realm-name>/protocol/openid-connect/token \
  -H "Content-Type: application/x-www-form-urlencoded" \
  -d "grant_type=password" \
  -d "client_id=<clientId>" \
  -d "client_secret=<clientSecret>" \
  -d "username=<user>" \
  -d "password=<password>"

Extract the access_token from the JSON response and pass it in the Authorization: Bearer <access_token> header for REST API, SpaceDeck, or XAP requests.
